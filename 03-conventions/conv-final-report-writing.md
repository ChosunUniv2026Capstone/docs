# 목적

이 문서는 캡스톤 최종보고서를 작성할 때 유지해야 하는 current truth 규약이다.
앞으로 새 보고서는 주간보고서가 아니라 최종보고서 형식으로 작성하며, 목차가 일부 바뀌더라도 아래 방향성은 유지한다.

# 핵심 방향

- 보고서 유형은 **최종보고서**를 기본으로 한다.
- 과거 주간보고서는 snapshot 으로만 유지하고, 새 주간보고서는 작성하지 않는다.
- 최종보고서의 1순위 논리축은 **구현 완성도 중심**이다.
- 구현 완성도는 단순 기능 나열이 아니라 **기능별 종합 증거 매트릭스**로 입증한다.
- 교수님 기준의 큰 구조는 유지하되, 실제 작성 시점의 완성도와 제출 목적에 맞게 목차 세부 항목은 조정할 수 있다.

# 교수님 기준 반영

최종보고서는 최소한 다음 큰 항목을 포함해야 한다.

1. 서론
   - 연구 배경
   - 필요성
   - 목적
2. 관련 연구 / 기술
   - 기존 방법 조사
   - 차별성 분석
3. 시스템 설계
   - 구조
   - 알고리즘
   - DB 설계
   - UML 등
4. 구현
   - 사용 기술
   - 개발 환경
   - 코드 구조
5. 실험 및 결과
   - 테스트 방법
   - 성능 평가
   - 한계점
6. 결론
   - 성과
   - 개선 방향
7. 참고문헌

보고서 품질 기준은 다음을 명시적으로 만족해야 한다.

- 논리성
- 자세한 기술 설명
- 객관적 근거
- 표 / 그림 캡션
- 참고문헌 형식

평가 포인트는 다음을 보여주는 방향으로 작성한다.

- 실제로 얼마나 깊게 수행했는가
- 기술 이해도
- 문제 해결 과정
- 문서 완성도

# 최종보고서 기본 배치

최종보고서의 앞부분은 다음 순서를 기본으로 한다.

1. 표지
2. 초록 / 요약
3. 목차
4. 이번 주 진행사항 및 전체 완성도 자체평가
5. 본문
6. 참고문헌
7. 부록

`이번 주 진행사항 및 전체 완성도 자체평가`는 주간보고서 대체물이 아니라, 최종보고서 앞에서 현재 진행 상태와 남은 보강 항목을 빠르게 보여주는 선행 섹션이다.

# 이번 주 진행사항 기준

매 보고서 작성 시 `이번 주 진행사항`의 기간은 다음과 같이 산정한다.

- 기준 시간대: KST, Asia/Seoul
- 시간 표기: `YYYY-MM-DD HH:MM KST` 형식을 사용하고, 본문 기준 시각/보고 기간 표기에는 UTC offset 표기를 붙이지 않는다.
- 시작 시각: 보고서 작성 시점 기준 직전 월요일 09:00 KST
- 종료 시각: 보고서 작성 현재 시각
- 포함 범위: 시작 시각 이상, 종료 시각 이하에 `main`으로 merge된 PR과 그 검증 결과

보고서 작성 시점이 월요일 09:00 KST 이전이면, 시작 시각은 전 주 월요일 09:00 KST 로 본다.
보고서 작성 시점이 월요일 09:00 KST 이후이면, 시작 시각은 해당 주 월요일 09:00 KST 로 본다.

# 기준 브랜치와 PR 개발기간 산정

변경사항과 현재 상태는 모든 레포의 `main` 브랜치를 기준으로 작성한다. 다만 이번 주 개발내용은 단순 commit 로그가 아니라 `main`으로 merge된 PR branch를 기준으로 산정한다.

- PR의 merge 시각이 보고 기간 안에 있으면 이번 주 개발내용으로 포함한다.
- 해당 PR의 개발 기간은 PR branch의 첫 commit 시각부터 PR merge 시각까지로 적는다.
- release-please/release PR은 기능 구현 PR과 구분하되, 이번 주 산출물 고정과 release manifest 정렬 근거로 포함한다.
- 로컬 작업 브랜치, 미병합 PR, 임시 변경사항은 최종보고서의 완료 근거로 쓰지 않는다.
- 필요하면 별도 `진행 중 / 미병합` 항목으로만 표시한다.

작성 순서는 반드시 `자연어 진행 요약 → 기능/문제 중심 상세 → PR 추적 근거 표` 순서로 둔다. PR 표만 나열하면 어떤 개발을 수행했는지 드러나지 않으므로, 먼저 “무엇을 만들었는지”, “어떤 문제를 발견했는지”, “어떤 부분을 고쳤는지”, “사용자에게 어떤 변화가 생겼는지”를 문단과 기능 중심 표로 설명한다. PR 번호와 branch/merge 시각은 그 설명을 검증하는 추적 근거로만 둔다.

기본 확인 대상 레포는 현재 workspace 의 git 레포 전체다.

- `Front`
- `Backend`
- `PresenceService`
- `DB`
- `Service`
- `docs`
- `CodexKit`
- `DocsQuartz`

보고서 작성 전에는 각 레포에서 다음을 확인한다.

- 현재 브랜치가 `main` 인지
- `origin/main` 과 동기화되어 있는지
- 보고 기간 안에 `main`으로 merge 된 PR과 각 PR의 첫 commit~merge 개발 기간이 무엇인지
- build / test / lint / health check 등 완료 근거가 있는지

# 기능별 종합 증거 매트릭스

구현 완성도는 기능별로 다음 항목을 함께 묶어 평가한다.

| 기능 영역 | 완료도 | 화면 근거 | API / 코드 근거 | DB 근거 | 테스트 / 실행 근거 | 한계 / 후속 과제 |
|---|---|---|---|---|---|---|
| 예: 인증 / 세션 | 완료 / 부분완료 / 후속 | 캡처 또는 화면 파일 | endpoint, 주요 코드 경로 | 관련 테이블 | 테스트 로그 | 남은 보강 |

완료도는 다음 기준으로 쓴다.

- `완료`: main 기준 구현과 검증 근거가 모두 있는 항목
- `로컬 MVP 완료`: 시연 가능한 구현과 로컬 검증은 있으나 운영 / 장기 현장 검증은 남은 항목
- `부분 완료`: 화면, API, DB, 테스트 중 일부 근거만 있는 항목
- `후속 과제`: 최종 성과가 아니라 개선 방향으로 분리해야 하는 항목

# 비범위와 한계 표현

다음 항목은 완료 성과로 표현하지 않는다.
반드시 한계점 또는 개선 방향으로 분리한다.

- 실운영 / 상용 배포 완료
- 장기 현장 검증 완료
- 학사시스템 정식 연동
- 네이티브 모바일 앱 구현

# 목차 작성 규칙

- 목차는 3계층까지 상세화할 수 있다.
- 매 보고서의 세부 목차는 변경될 수 있다.
- 단, 교수님 기준의 큰 항목과 구현 완성도 중심의 논리축은 유지한다.
- 미완 기능은 구현 성과 장이 아니라 한계점, 개선 방향, 후속 과제 장으로 이동한다.
- 표와 그림에는 본문에서 참조 가능한 번호와 캡션을 붙인다.
- 참고문헌은 일관된 형식을 사용하고, 공식 문서 / 논문 / 프로젝트 내부 문서를 구분한다.

# 권장 3계층 큰 틀

다음 구조를 기본 출발점으로 사용한다. 실제 보고서 작성 시 세부 항목은 현재 완성도와 제출 요구에 맞게 조정할 수 있다.

1. 서론
   1. 연구 배경
      1. 기존 사이버캠퍼스의 역할과 한계
      2. 출석 / 시험 신뢰성 문제
      3. Wi-Fi 기반 재실성 판별 도입 배경
   2. 연구 필요성
      1. 대리출석 및 비정상 출석 문제
      2. 단순 로그인 기반 인증의 한계
      3. 실내 위치 기반 인증의 필요성
   3. 연구 목적과 범위
      1. 차세대 사이버캠퍼스 프로토타입 구현
      2. 등록 단말 기반 출석 신뢰성 강화
      3. 실운영 / 장기 현장 검증 / 학사시스템 연동 / 모바일 앱 제외 범위
2. 관련 연구 및 기술
   1. 기존 LMS 및 출석 관리 방식
      1. 일반 LMS 기능 구조
      2. 출석 인증 방식 비교
      3. 기존 방식의 한계
   2. 위치 / 단말 기반 인증 기술
      1. GPS, QR, BLE, Wi-Fi 방식 비교
      2. 등록 단말 기반 인증
      3. 랜덤 MAC 및 개인정보 처리 한계
   3. 차별성 분석
      1. LMS 와 재실성 판별 결합
      2. PresenceService 분리 구조
      3. 출석과 시험 접근 제어 연계
3. 시스템 설계
   1. 전체 시스템 구조
      1. Front / Backend / PresenceService / DB / Service 구성
      2. Nginx 단일 진입점
      3. Docker Compose 로컬 실행 구조
   2. 핵심 알고리즘
      1. AP snapshot 수집
      2. 등록 단말 매칭
      3. RSSI threshold 기반 eligibility 판정
   3. DB 및 UML 설계
      1. 사용자 / 강의 / 수강 관계
      2. 단말 / 강의실 / AP 관계
      3. 출석 / 시험 시퀀스 다이어그램
4. 구현
   1. 사용 기술과 개발 환경
      1. React + Vite
      2. FastAPI + Redis
      3. PostgreSQL + Docker Compose
   2. 서비스별 구현
      1. Front 역할별 UI
      2. Backend LMS / 출석 / 시험 API
      3. PresenceService eligibility / collector / demo overlay
   3. 코드 구조와 주요 구현 포인트
      1. 인증 / 세션 구조
      2. 출석 workflow
      3. 시험 workflow
5. 실험 및 결과
   1. 테스트 방법
      1. Front build / lint
      2. Backend pytest
      3. PresenceService pytest
   2. 기능 검증 결과
      1. 기능별 종합 증거 매트릭스
      2. 출석 workflow 검증
      3. 시험 workflow 검증
   3. 성능 평가와 한계점
      1. Redis snapshot cache 효과
      2. OpenWrt collector push 구조
      3. 로컬 MVP 및 현장 검증 한계
6. 결론
   1. 성과
      1. LMS 핵심 기능 구현 성과
      2. 재실성 기반 출석 판정 구현 성과
      3. 시험 접근 제어 연계 성과
   2. 문제 해결 과정
      1. 출석 신뢰성 문제 정의
      2. 서비스 분리 설계 결정
      3. 로컬 MVP 검증
   3. 개선 방향
      1. 장기 현장 테스트
      2. 개인정보 / 보안 정책 보강

   1. 학술 자료

      2. Wi-Fi 기반 실내 위치 추정

   2. 기술 문서
      1. FastAPI / React / Vite
      2. PostgreSQL / Redis
      3. OpenWrt
   3. 프로젝트 내부 문서
      1. 요구사항 문서
      2. 아키텍처 문서
      3. 구현 로드맵 / 상태 문서
8. 부록
   1. 화면 캡처 목록
      1. 학생 화면
      2. 교수 화면
      3. 관리자 화면
   2. API 명세 요약
      1. 인증 / 강의 / 공지 API
      2. 출석 / 시험 API
      3. PresenceService API
   3. DB ERD 및 테스트 로그
      1. ERD
      2. 테스트 로그
      3. 실행 / health check 결과

# 2파일 최종 산출물 원칙

최종 제출/검토자가 실제로 읽어야 하는 파일은 다음 두 개로 고정한다.

1. `docs/08-reports/99-combined-report.md` — 보고서
2. `docs/08-reports/99-combined-report-appendix.md` — 부록

다른 보고서 조각, 과거 부록, architecture/status/convention 문서는 작성 근거로만 사용한다. 최종 독자는 위 두 파일만 열어도 프로젝트 목표, 설계, 구현, 화면 흐름, 코드, DB/ERD, 검증, 한계를 이해할 수 있어야 한다.
