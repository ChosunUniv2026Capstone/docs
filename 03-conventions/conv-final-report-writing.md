# 목적

이 문서는 캡스톤 최종보고서를 작성할 때 유지해야 하는 current truth 규약이다.
앞으로 새 보고서는 주간보고서가 아니라 최종보고서 형식으로 작성하며, 본문 구성이 일부 바뀌더라도 아래 방향성은 유지한다.

# 핵심 방향

- 보고서 유형은 **최종보고서**를 기본으로 한다.
- 과거 주간보고서는 snapshot 으로만 유지하고, 새 주간보고서는 작성하지 않는다.
- 최종보고서의 1순위 논리축은 **구현 완성도 중심**이다.
- 구현 완성도는 단순 기능 나열이 아니라 **기능별 종합 증거 매트릭스**로 입증한다.
- 교수님 기준의 큰 구조는 유지하되, 실제 작성 시점의 완성도와 제출 목적에 맞게 본문 구성 세부 항목은 조정할 수 있다.

# 교수님 기준 반영

최종보고서는 최소한 다음 큰 항목을 포함해야 한다.

1. 서론
   - 연구 배경
   - 필요성
   - 목적
2. 관련 연구 / 기술
   - 기존 방법 조사
   - 차별성 분석
3. 시스템 설계
   - 구조
   - 알고리즘
   - DB 설계
   - UML 등
4. 구현
   - 사용 기술
   - 개발 환경
   - 코드 구조
5. 실험 및 결과
   - 테스트 방법
   - 성능 평가
   - 한계점
6. 결론
   - 성과
   - 개선 방향
7. 참고문헌

보고서 품질 기준은 다음을 명시적으로 만족해야 한다.

- 논리성
- 자세한 기술 설명
- 객관적 근거
- 표 / 그림 캡션
- 참고문헌 형식

평가 포인트는 다음을 보여주는 방향으로 작성한다.

- 실제로 얼마나 깊게 수행했는가
- 기술 이해도
- 문제 해결 과정
- 문서 완성도

# 최종보고서 기본 배치

최종보고서의 앞부분은 다음 순서를 기본으로 한다.

1. 표지
2. 초록 / 요약
3. 이번 주 진행사항 및 전체 완성도 자체평가
4. 본문
5. 참고문헌
6. 부록

보고서 파일에는 차례/목차 페이지를 자동으로 넣지 않는다. 차례는 보고서 작성이 완료된 뒤 사용자가 HWP 편집기에서 직접 입력하거나 생성해야 한다. 따라서 보고서 작성 완료 안내에는 반드시 "차례는 한글에서 사용자가 직접 입력/생성해야 합니다"라는 취지의 문장을 포함한다.

보고서 문서 산출물은 앞으로 **HWP만 생성**한다. HWPX는 중간 검증용이나 제출용 산출물로 생성하지 않는다. HWP 검증은 한글 GUI가 아니라 `rhwp info`, `rhwp export-text`, `rhwp export-png`, HTML/PDF 렌더링 검증으로 수행한다.

`이번 주 진행사항 및 전체 완성도 자체평가`는 주간보고서 대체물이 아니라, 최종보고서 앞에서 현재 진행 상태와 남은 보강 항목을 빠르게 보여주는 선행 섹션이다.

# 이번 주 진행사항 기준

매 보고서 작성 시 `이번 주 진행사항`의 기간은 다음과 같이 산정한다.

- 기준 시간대: KST, Asia/Seoul
- 시간 표기: `YYYY-MM-DD HH:MM KST` 형식을 사용하고, 본문 기준 시각/보고 기간 표기에는 UTC offset 표기를 붙이지 않는다.
- 시작 시각: 보고서 작성 시점 기준 직전 월요일 09:00 KST
- 종료 시각: 보고서 작성 현재 시각
- 포함 범위: 시작 시각 이상, 종료 시각 이하에 `main`으로 merge된 PR과 그 검증 결과

보고서 작성 시점이 월요일 09:00 KST 이전이면, 시작 시각은 전 주 월요일 09:00 KST 로 본다.
보고서 작성 시점이 월요일 09:00 KST 이후이면, 시작 시각은 해당 주 월요일 09:00 KST 로 본다.

# 기준 브랜치와 PR 개발기간 산정

변경사항과 현재 상태는 모든 레포의 `main` 브랜치를 기준으로 작성한다. 다만 이번 주 개발내용은 단순 commit 로그가 아니라 `main`으로 merge된 PR branch를 기준으로 산정한다.

- PR의 merge 시각이 보고 기간 안에 있으면 이번 주 개발내용으로 포함한다.
- 해당 PR의 개발 기간은 PR branch의 첫 commit 시각부터 PR merge 시각까지로 적는다.
- release-please/release PR은 기능 구현 PR과 구분하되, 이번 주 산출물 고정과 release manifest 정렬 근거로 포함한다.
- 로컬 작업 브랜치, 미병합 PR, 임시 변경사항은 최종보고서의 완료 근거로 쓰지 않는다.
- 필요하면 별도 `진행 중 / 미병합` 항목으로만 표시한다.

작성 순서는 반드시 `자연어 진행 요약 → 기능/문제 중심 상세 → PR 추적 근거 표` 순서로 둔다. PR 표만 나열하면 어떤 개발을 수행했는지 드러나지 않으므로, 먼저 “무엇을 만들었는지”, “어떤 문제를 발견했는지”, “어떤 부분을 고쳤는지”, “사용자에게 어떤 변화가 생겼는지”를 문단과 기능 중심 표로 설명한다. PR 번호와 branch/merge 시각은 그 설명을 검증하는 추적 근거로만 둔다.

기본 확인 대상 레포는 현재 workspace 의 git 레포 전체다.

- `Front`
- `Backend`
- `PresenceService`
- `DB`
- `Service`
- `docs`
- `CodexKit`
- `DocsQuartz`

보고서 작성 전에는 각 레포에서 다음을 확인한다.

- 현재 브랜치가 `main` 인지
- `origin/main` 과 동기화되어 있는지
- 보고 기간 안에 `main`으로 merge 된 PR과 각 PR의 첫 commit~merge 개발 기간이 무엇인지
- build / test / lint / health check 등 완료 근거가 있는지

# 기능별 종합 증거 매트릭스

구현 완성도는 기능별로 다음 항목을 함께 묶어 평가한다.

| 기능 영역 | 완료도 | 화면 근거 | API / 코드 근거 | DB 근거 | 테스트 / 실행 근거 | 한계 / 후속 과제 |
|---|---|---|---|---|---|---|
| 예: 인증 / 세션 | 완료 / 부분완료 / 후속 | 캡처 또는 화면 파일 | endpoint, 주요 코드 경로 | 관련 테이블 | 테스트 로그 | 남은 보강 |

완료도는 다음 기준으로 쓴다.

- `완료`: main 기준 구현과 검증 근거가 모두 있는 항목
- `로컬 MVP 완료`: 시연 가능한 구현과 로컬 검증은 있으나 운영 / 장기 현장 검증은 남은 항목
- `부분 완료`: 화면, API, DB, 테스트 중 일부 근거만 있는 항목
- `후속 과제`: 최종 성과가 아니라 개선 방향으로 분리해야 하는 항목

# 비범위와 한계 표현

다음 항목은 완료 성과로 표현하지 않는다.
반드시 한계점 또는 개선 방향으로 분리한다.

- 실운영 / 상용 배포 완료
- 장기 현장 검증 완료
- 학사시스템 정식 연동
- 네이티브 모바일 앱 구현

# 본문 구성과 차례 처리 규칙

- 본문 제목 구조는 3계층까지 상세화할 수 있다.
- 매 보고서의 세부 본문 구성은 변경될 수 있다.
- 단, 교수님 기준의 큰 항목과 구현 완성도 중심의 논리축은 유지한다.
- 보고서 산출물에는 차례/목차 페이지를 자동 삽입하지 않는다.
- 이전 참고 파일에 차례가 있더라도, 앞으로는 차례 형식만 참고하지 않고 산출물에는 넣지 않는다.
- 보고서 작성 완료 후 사용자에게 차례는 HWP 편집기에서 직접 입력하거나 생성해야 한다고 다시 알려준다.
- 미완 기능은 구현 성과 장이 아니라 한계점, 개선 방향, 후속 과제 장으로 이동한다.
- 표와 그림에는 본문에서 참조 가능한 번호와 캡션을 붙인다.
- 참고문헌은 일관된 형식을 사용하고, 공식 문서 / 논문 / 프로젝트 내부 문서를 구분한다.

# 화면 캡처와 그림 배치 규칙

최종보고서와 부록의 화면 캡처는 독자가 해당 기능을 바로 확인할 수 있도록 다음 규칙을 따른다.

- 설명 대상 UI는 redbox 주석 SVG 안에서 바로 보여야 하며, 다른 파일을 추가로 열어야 이해되는 방식은 피한다.
- 캡처가 세로로 길어져 가로:세로 비율이 1:1을 초과하면, 전체 페이지를 그대로 넣지 말고 설명에 필요한 redbox 주변 영역만 잘라 사용한다.
- 크롭 후 화면 캡처는 원칙적으로 `height <= width`가 되도록 맞춘다. 단, ERD처럼 전체 구조 확인이 목적이고 세부 분할 그림을 별도로 제공하는 경우는 예외로 둘 수 있다.
- 원본 PNG를 교체하거나 크롭하면 해당 redbox SVG의 embedded image data, `viewBox`, redbox 좌표, 라벨 좌표도 함께 갱신한다.
- 너무 긴 workflow는 한 장에 억지로 담지 말고 기능별로 여러 Fig.로 분리한다. 각 Fig.는 본문 캡션과 정확히 같은 화면 요소만 강조한다.

# HTML redbox 캡처 규칙

앞으로 최종보고서에 들어가는 redbox 화면은 SVG를 최종 이미지 위에 다시 합성하지 않는다. 가능한 경우 실제 서비스 화면에 접속한 뒤 DOM에 강조용 요소를 삽입하고 그 상태를 캡처한다.

- 실제 웹 화면은 Playwright / Browser / Computer Use 중 접근 가능한 도구로 서비스에 접속한 뒤, 캡처 직전에 대상 DOM 요소에 redbox와 라벨을 삽입한다.
- redbox는 대상 요소 바깥으로 최소 6px 이상 여백을 두고, 화면 가장자리에 닿지 않게 한다.
- 캡처 영역은 redbox 주변 여백을 포함해 잘라내며, 설명 대상과 무관한 페이지 하단까지 포함하지 않는다.
- 기존 PNG, ERD SVG, 외부 이미지처럼 HTML 화면이 아닌 근거 자료는 `원본 이미지 + HTML overlay harness` 방식으로 다시 렌더링한다. 즉 원본 이미지를 `<img>`로 배치하고 redbox와 라벨을 HTML 요소로 올린 뒤 브라우저 screenshot을 찍는다.
- 최종 보고서 Markdown과 HWP에는 `docs/08-reports/assets/**/html-redbox/*.png` 경로의 PNG를 사용한다. 기존 `final/annotated/*.svg`는 좌표 원장으로만 유지한다.

캡처 QA는 다음 항목을 자동으로 검사한다.

- redbox 좌표가 캔버스 밖으로 나가지 않았는지 확인한다.
- 최종 PNG에서 red pixel이 예상 redbox 상/하/좌/우 경계에 존재하는지 pixel sampling으로 확인한다.
- redbox 라벨은 브라우저 DOM 기준 `scrollWidth <= clientWidth` 및 `scrollHeight <= clientHeight`를 만족해야 한다.
- 과거 고정 박스 기준 `360x40`에서 넘치는 라벨도 기록해, 라벨이 길면 자동 줄바꿈/상자 확장으로 보정한다.
- 최종 QA 산출물은 `output/full-report-2026-06-01/qa/html-redbox-assets.json`과 `html-redbox-assets.md`에 남긴다.

# 한국어 stop-slop 문체 QA

`hardikpandya/stop-slop`의 원칙은 영어 문구 삭제, 구조적 클리셰 제거, 능동문, 구체성, 리듬 변화, 독자 신뢰를 핵심으로 한다. 한국어 보고서에는 이를 그대로 번역하지 않고 다음 규칙으로 적용한다.

- 제출용 본문에는 `ChatGPT`, `AI가 작성`, `인공지능이 작성`, `AI 어시스턴트` 같은 작성 주체 노출 문구를 남기지 않는다.
- `본 보고서에서는`, `본 장에서는`, `살펴보고자 한다`처럼 내용을 예고만 하는 문장은 실제 주장이나 근거 문장으로 바꾼다.
- `이를 통해 ... 기대할 수 있다`, `사용자 편의성 향상`, `체계적인/효과적인/원활한` 같은 추상적 효익 문구는 구체 화면, 동작, 테스트, 수치 중 하나로 바꾼다.
- `확인할 수 있다`, `볼 수 있다`가 반복되면 직접 서술로 줄인다. 예: `학생 대시보드는 마감 과제를 날짜별로 표시한다`.
- 수동형 문장은 행위자가 분명한 경우 행위자와 동작을 앞에 둔다. 단, 기술 보고서에서 자연스러운 상태 설명은 경고로만 다룬다.
- 자동 QA는 차단 규칙과 경고 규칙을 분리한다. 차단 규칙은 실패로 처리하고, 경고 규칙은 반복 패턴을 줄이기 위한 수정 후보로 남긴다.

한국어 문체 QA 산출물은 `output/full-report-2026-06-01/qa/korean-stop-slop.json`과 `korean-stop-slop.md`로 남긴다.
